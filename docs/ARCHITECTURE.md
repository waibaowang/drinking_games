# 架构说明

## 部署边界

系统是单服务器模块化单体，面向约 20 名熟人、同时 1～3 桌。Spring Boot 同时承载 REST、STOMP 和行动计时器；PostgreSQL 是账号、活跃房间和历史记录的事实来源。聊天不持久化。

## 一次状态变更

```text
客户端意图（actionId + expectedVersion）
  → 房间级同步锁
  → 若 actionId 已处理，直接返回最新状态
  → 从持久状态克隆候选牌桌
  → 在候选上校验并执行
  → PostgreSQL 事务提交快照、截止时间及必要的历史记录
  → 替换内存牌桌
  → 为每位成员生成脱敏视图并广播
```

数据库提交失败时不会替换内存状态。普通行动和超时回调在同一房间锁内比较牌桌版本，因此只能有一方成功。最近 128 个 `actionId` 随房间快照保存，重启后仍能去重。

## 快照与恢复

`poker_rooms.state_json` 保存内部快照：所有座位、筹码、下注、状态、底牌、公共牌、完整牌堆与游标、街道、按钮/盲注位置、待行动集合、每位玩家上次面对的下注额、消息、洗牌种子和承诺。普通玩家 DTO、管理员接口和日志都不返回这些秘密字段。恢复时会校验玩家、座位、筹码、牌组、游标以及种子/承诺的一致性，异常快照不会被静默加载。

启动时只加载 `ACTIVE` 房间：

- `SHUFFLE_PENDING` 会使用已保存的牌堆继续发牌，不重新洗牌；
- 行动截止时间未到，按剩余时间重新调度；
- 已过期，立即执行一次自动过牌或弃牌；
- 玩家重新登录后从“我的牌局”返回原桌。

`recovered` 是本次进程加载产生的提示标记，不影响游戏规则。

## 两阶段洗牌

1. `prepareHand()` 用 `SecureRandom` 生成 256 位种子和牌序，保存 SHA-256 承诺、种子与牌堆，此时没有底牌。
2. 快照提交成功后，服务端发送独立的 `/shuffle` 事件，并广播承诺状态。
3. 随后 `dealPreparedHand()` 从同一已保存牌堆发牌。
4. 手牌完成后，仅在玩家视图中公开种子。

STOMP broker 保持发布顺序，确保承诺事件先于含底牌的状态。

## 权限

- 数据库角色为 `ADMIN` 或 `PLAYER`；管理员也能正常参与牌局。
- HTTP 每次请求都会重新检查账号是否启用以及 `auth_version`；禁用、重置密码或修改角色会使已有会话失效，重新启用也不会复活旧会话。
- STOMP 入站和出站拦截器对已连接会话执行相同检查；失效连接不能继续操作，也不会再收到私有牌桌消息。
- `/api/admin/**` 要求 `ADMIN`。
- 历史查询必须通过 `hand_record_players` 验证参与关系。
- 房间状态通过用户私有队列发送；进行中的底牌只出现在本人的视图中。

## 数据表

- `user_accounts`：账号、BCrypt 哈希、角色、启用状态、会话版本和时间戳。
- `poker_rooms`：房间元数据、状态、截止时间、乐观版本和内部 JSON 快照。
- `room_members`：房间成员，用于“我的牌局”和访问控制。
- `hand_records`：完成手牌的结算摘要。
- `hand_record_players`：历史记录参与者授权。

水平扩展、跨节点房间租约和外部消息系统不在当前范围内。
