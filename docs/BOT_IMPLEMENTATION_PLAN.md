# 双游戏机器人实施方案（已确认，实施中）

## 目标与范围

用户已确认飞行棋和德州扑克都支持机器人，用于独自游玩和测试。一个真实玩家加至少一个机器人即可开局；飞行棋最多四个座位，德州不超过房间原有座位上限。

复用现有 Java 单体、规则引擎、Vue 页面和房间持久化。机器人在服务器内运行，不建立可登录账号，不使用大模型、外部 API、独立进程、Redis 或新依赖。本期只有一种基础策略，目标是稳定推进游戏，不追求专业对战水平。

暂不做纯机器人自对局、自动创建房间或自动连续开新局；含机器人时，开局需要至少一名真人入座，每局/每手仍由房主开始。真人操作规则不变：飞行棋不限时，德州保留原有行动期限。

## 房间操作与页面

- 房主可在等待开局或上一局/手结束后添加、移除机器人；进行中不能换人。
- 提供“添加机器人”和“补齐空位”，也允许选择空颜色/空座位添加。满座时禁用，不能覆盖真人。
- 座位名称显示“机器人 1”等明显标识；其他玩家能看见，但不能控制或代替机器人操作。
- 房主可随时“暂停机器人 / 继续机器人”。只暂停机器人自动操作，不停止真人操作或真人原有倒计时；轮到已暂停机器人时等待继续，不能被德州超时逻辑偷偷代打。
- 默认正常速度，每次操作约 800 毫秒；提供快速测试速度约 200 毫秒。飞行棋掷骰和选飞机分开执行，保证结果看得清。
- 德州机器人初始筹码使用房间配置，不自动补充。筹码用完后在两手之间提示移除并重新添加，避免暗中改变筹码总量。
- 机器人不聊天，没有个人资料页，不出现在管理后台的账号列表中。

## 两种游戏的策略

### 飞行棋

自动掷骰，点数仍由原规则引擎生成，机器人不能指定结果。只从服务器给出的合法飞机中选择，优先到达终点、撞机，再考虑起飞和推进；同等选择加入少量随机性。

如需评估移动结果，在隔离的候选状态中调用原移动规则，不另写跳跃、反弹、撞机计算。不预掷下一次骰子，不窥探未来道具刷新。不添加道具效果。5/6 起飞、连续 6 无上限和道具刷新规则均不变。

### 德州扑克

机器人只接收 `snapshotFor(botId)` 的本人视图：自己的底牌、公共牌、下注和筹码、本人合法动作。策略模块不得接触完整内部快照、其他玩家底牌、剩余牌堆或洗牌种子。

使用基础启发式：可以过牌时通常过牌；根据自己牌力和跟注代价选择跟注或弃牌；较强牌有一定概率下注/加注。严格遵守合法动作、最小加注、短码 All-in 和加注权，不把 All-in 当作默认策略。复用现有牌型评估代码，不进行高成本模拟搜索或“必赢”设计。

## 服务器执行与安全

复用协调层的候选状态执行路径：克隆 → 规则校验 → 数据库保存 → 替换内存 → 广播。将共同的受校验提交部分提取为小方法，不增加通用游戏框架。

真人 HTTP/STOMP 仍按当前登录身份授权。机器人只走服务端内部入口，客户端不能传一个机器人 ID 就控制它。添加、移除、暂停和速度设置都要验证房主身份及房间状态。

使用一个轻量共享调度器；每个房间最多一个待执行机器人动作，不为每个机器人建立线程。调度任务记录房间、预期状态版本、当前操作者和一次操作 UUID，执行前在房间锁内再次验证。旧任务、重复任务或已经关闭的房间直接作废，不重复掷骰或扣筹码。

执行一次机器人动作后，再根据已提交状态安排下一次动作，不用递归或无限 while 循环。保存失败不能推进内存；有限延迟重试期间保留同一个动作身份，状态已变化就取消。德州自动动作与现有超时共用版本保护；不能同时产生两次行动。

没有真人连接并订阅房间时不安排机器人动作；新订阅/断开事件更新房间在线状态，同一个人多标签页断开一页不算全部离线。后台重启后先恢复房间，真人重新登录订阅后再按当前操作者恢复调度。房间关闭、暂停或服务停止时取消待执行任务。

## 数据与兼容

现有 `room_members`、`flight_room_members` 和 `hand_record_players` 对用户名有账号外键，不能把虚构机器人用户名直接写入这些表。

- 机器人使用不可注册的内部 ID，与真人账号命名空间隔离，不加入真人成员表。
- 在两种房间已有的持久化快照包装层增加机器人座位名单、运行开关和速度，不改规则状态中的牌堆、骰子等格式，不新增机器人表。
- 旧快照缺少新字段时按“没有机器人、正常速度”读取，增加旧快照恢复测试；预期不需要 Flyway 表结构迁移。
- 公开 `RoomState` / `FlightRoomState` 增加安全的机器人元信息，前端据此显示标识与控制；不会返回秘密状态。
- 完成记录的可见参与者仅写入真实账号，结算摘要仍包含机器人名称及游戏结果；两种游戏都要修正历史写入，防止完成时触发外键错误。
- 升级前备份数据库；回退不认识机器人的旧包前，先结束或关闭所有含机器人的房间，不能直接让旧版本加载新机器人快照。

## 建议接口

两种游戏共用房间路由，由已有房间类型分发：

- `POST /api/rooms/{roomId}/bots`：添加指定空座位的一个机器人。
- `POST /api/rooms/{roomId}/bots/fill`：原子补齐当前空位，不能部分成功却返回失败。
- `DELETE /api/rooms/{roomId}/bots/{botId}`：移除指定机器人。
- `PATCH /api/rooms/{roomId}/bots/settings`：设置启停和正常/快速速度。

所有修改成功后广播房间最新状态。请求不接受机器人策略、底牌、骰子点数或任意账号身份。公开类型及 API 文档同步更新。

## 验证与执行顺序

先完成飞行棋 UI 第二轮独立复查，再实施此方案。机器人功能最多三轮，多 Agent 文件职责分开：飞行棋策略与测试、德州策略与测试、前端控制；主 Agent 负责共享调度、权限、快照兼容、联调和提交。

1. 第一轮完整实现并验证：一个真人加三个飞行棋机器人；一个真人加多个德州机器人，完成多手牌。两种历史均正常，未新增机器人登录账号。
2. 第二轮整体复查：非房主操作、满座/真人座位、客户端冒充机器人、底牌隔离、旧快照恢复、重启继续、暂停、多人多标签页离线、关房、数据库失败和机器人/超时并发。随机对局检查牌/飞机合法性与筹码守恒。
3. 只有仍存在验收问题才进入第三轮，修复问题后交付，不增加额外机器人功能；第二轮通过则停止。

策略测试使用可控随机源和时钟/调度器，不靠长时间等待或修改生产骰子。全量 `mvn verify`、前端测试/类型检查/生产构建、统一验证脚本及 `git diff --check` 都要通过。

每阶段更新 `docs/IMPLEMENTATION_PROGRESS.md`，每轮独立提交，记录测试结果、遗留项与恢复入口。额度中断后以进度文档和提交为准继续，不能重置现有用户或房间。
